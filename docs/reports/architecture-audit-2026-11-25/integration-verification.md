# Интеграционная приёмка My Island

Интеграционная ветка собирает функциональные изменения из реестра аудита от 25 ноября 2026 года. PR предназначен для совместных проверок. Предыдущая версия для сравнения — main на 6eda54a. Отдельные Draft PR остаются точками ревью и выпуска. [Интеграционный PR №61](https://github.com/Surpd/my-island/pull/61) · [Реестр и зависимости](implementation.md).

## Что проверяет интеграция

- Полный Python unittest discovery сравнивается с локальным запуском исходной main, где выполнено 773 теста, включая 14 пропусков опциональных сценариев. PostgreSQL-сценарии запускаются отдельными заданиями на PostgreSQL 17 с loopback DSN.
- Frontend CI выполняет Node unit tests, TypeScript, lint и production build с явным loopback VITE_API_BASE_URL. Отдельные Chromium runner выполняют все части существующего Playwright набора, каждая часть работает со своей маркированной SQLite fixture.
- В изолированном e2e-профиле адрес /admin/architecture-check?role=admin открывает проверочный интерфейс. Он использует существующую административную авторизацию и реальные API рабочего дня, нагрузки, классов, журналов и раскладок. Тест проходит каждую выборку через браузер. Сценарии Campus и конструктора также проверяются существующими наборами.
- Рабочая схема PostgreSQL для теста реконструируется из миграций до 053. При свежей сборке фикстуры миграция 016 требует убрать уже созданный 013 триггер перед его определением. Планировщик pg_cron/pg_net из 044 зависит от Supabase. Из 045 воспроизводится схема без одноразовой переклассификации конкретного рабочего журнала. Эти особенности относятся к тестовой подготовке предыдущей схемы. Миграции 054–058 исполняются целиком по порядку.
- Между предыдущей схемой и 054–058 помещаются синтетические записи. Проверяются их сохранность, версия старых карточек, связи, RLS и отсутствие фиктивных событий. Пустая копия схемы используется отдельными транзакционными тестами публикации и импорта. Другие задания проверяют справочник, воркеры Sheets и раскладки отдельными соединениями.
- Производительность аналитики измеряется на 960 синтетических назначениях, без сетевого обращения к школьному инстансу. Результат характеризует число SQL-вызовов и время на runner. Задержка на малом инстансе Render проверяется отдельно при согласованном выпуске.

## Последовательность слияния после приёмки

1. Принять №48 и №52. Перед слиянием №53 убедиться, что перенесённые изменения №52 не создают вторую реализацию диапазона. Принять №53 и затем №56.
2. Принять №49, затем №59 с историей и проверкой конкурирующих редакторов. Принять №50, затем №58.
3. После №48 принять №54. После №54 и №53 принять №60. Клиентская интеграция виджетов зависит также от №59 и выбора дизайна.
4. После №48 принять №55. №57 требует отдельной приёмки на выделенной тестовой книге перед включением доставки. Выпуск недельной публикации и включение доставки могут происходить раздельно.
5. Принять документационный №47 и проверить последовательность зависимых веток заново на текущей main. Интеграционный PR можно сохранить как проверочный артефакт.

## Выпуск и откат

1. Сверить точные идентификаторы My Island в .project-identity.json. Для школьной базы подготовить резервную копию и проверить возможность восстановления в отдельном окружении. Применить миграции 054–058 в числовом порядке только после отдельного разрешения.
2. Проверить чтение и действующие роли после схемы. Согласованно выпустить backend Render и фронтенд GPT Sites. Открытая старая форма справочника при записи без ревизии получает HTTP 428, существующая карточка сохраняется. Предупредить администраторов о необходимости обновить открытые вкладки до сохранения. Запрос публикации старого клиента проходит переходный контракт, восстановление квитанций доступно обновлённому клиенту.
3. Проверить синтетическими тестовыми пользователями на согласованном окружении Campus, preview, рабочий день, справочник, архив публикаций и журналы. Включить рабочий экспорт только после испытания на отдельной разрешённой книге. Для одновременной ручной правки управляемого диапазона Google остаётся окно между внешним чтением и записью.
4. При проблеме доставки выключить её флаг, сохранить идентификаторы вкладок и очередь. При проблеме клиента откатить версии фронтенда и backend по согласованному пути, сохранив добавленные таблицы и данные. Учесть, что прежний backend использует прежние правила конкуренции. Для возврата содержимого недели использовать проверенное восстановление редакции с новой квитанцией. Удаление истории или миграций из рабочей схемы не входит в откат.

Визуальная приёмка новых экранов относится к отдельному PR №51. Для расчёта официальной нагрузки и кабинетов ещё нужны школьные правила и подтверждённый каталог. Агрегаты описывают расписание, а фактическое проведение требует отдельного источника.


## Ошибки полной проверки и воспроизводимость

Первые интеграционные Chromium прогоны выявили устаревшие сценарии, которые не запускались в части профильных CI. На main 6eda54a совпали дубль кнопок сохранения и устаревшая надпись диагностики. Ещё три сценария ссылались на кнопку, которой уже нет в исходниках main. Исправленные проверки работают через текущие контролы с прежними проверками запроса, состояния, ошибок и перечитывания. Журнальные сценарии используют разрешённые тестовые вкладки и проверяют полугодия в старших классах, триместры и реальную вкладку «По работам». Вторая Chromium конфигурация проверяет школьный профиль и обе проверки, пропускаемые в demo.
