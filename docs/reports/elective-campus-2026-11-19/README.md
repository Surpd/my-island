# Общие блоки курсов по выбору и Campus

Базовая версия: `f2c5ff4ad9c8ea72624d4bfcbf58c23ab5e48bee` (`main`).

## Реализация

- Направления остаются отдельными административными занятиями с собственными преподавателями и кабинетами. `blockId`/`blockName` связывают параллельные направления в один блок; название по умолчанию — «Курс по выбору».
- Администратор может создать общий блок, переименовать его и безопасно сопоставить существующее или историческое направление с блоком. Сопоставление не выбирает курс за ученика и не сохраняет персональных назначений.
- При публикации старое занятие без `activityType` распознаётся как курс только при наличии явного `blockId` и одного из известных названий общего блока. Обычные занятия не переклассифицируются по своему названию или совпадению времени. Неоднозначные записи без устойчивой связи остаются в источнике и получают причину `elective_block_unlinked`.
- Student Campus показывает одну нейтральную карточку на каждый блок и временной интервал, доступный классу ученика. В ней нет направления, списка вариантов, кабинета и преподавателя. Кружки не попадают ни в основные занятия, ни в `optional_activities` Student Campus.
- Teacher Campus по-прежнему получает конкретные занятия из своих назначений; общая подпись блока используется только для ученической проекции.
- Параллельные направления одного блока не конфликтуют между собой по ученикам. Реальные пересечения по преподавателям и кабинетам проверяются по отдельным назначениям, а подтверждённые участники используются для проверки пересечения с обязательным уроком. Неизвестные группы не добавляются в аудиторию.
- Сводка публикации различает исходные строки, карточки Campus, общие блоки и направления, скрытые кружки, неразрешённые персональные назначения и не блокирующие предупреждения. Полный исходный список и версия расписания сохраняются.
- `_admin_week_history()` передаёт `week:%` параметром, совместимым с SQLite и psycopg.

Исходные черновики и production-данные не изменялись. Миграций нет; для поведения интерфейса потребуется frontend-релиз после обычного процесса выпуска.

## Дополнение PR #9 · групповые связи и legacy публикации

- В школьном конструкторе есть групповое сопоставление ровно выбранных несвязанных направлений. До фиксации администратор видит состав, классы и время; каждое сопоставление требует одного явного подтверждения. Автосвязи по названию или времени нет.
- Старые authoritative публикации, где у канонического блока все явные элективные строки без `blockId`, остаются видимыми как одна нейтральная карточка. Она не раскрывает направление, преподавателя или кабинет и не приписывает ученика к группе. В provenance выставляется `requires_administrative_block_mapping`; если строки нельзя уверенно связать в одном canonical-блоке, автоматическое объединение не выполняется.
- `_projection_mismatches()` дополнительно проверяет обязательные назначения блока после успешной elective-проекции. Кэширование ограничено одинаковым grade/membership pattern и ключом блока; аудитория с индивидуальными include/exclude правилами, нерешёнными участниками или подтверждённым конфликтом остаётся персональной.
- Добавлены адресный тест legacy digital-публикации, тест против маскировки ошибки обязательного урока elective-веткой и отдельная производительная регрессия.

### Измеренная производительность

Локальный синтетический прогон строит 357 строк, 7 параллелей, 175 учеников с двумя членствами на ученика и 35 преподавателей. После кэширования одинаковых проекций он измеряет SQL statements через SQLite trace callback, вызовы и время `_project_student_block()`, а также длительность `_projection_mismatches()` и `experiment_audience_preview()`. Последний прогон: **465.5 мс всего, 41 SQL statement, 696 персональных canonical-проекций (53.9 мс внутри проектора), `_projection_mismatches()` 261.3 мс, `experiment_audience_preview()` 80.7 мс**. До кэширования тот же synthetic pattern создавал 8700 вызовов и занимал около 2.3 с. Эти цифры относятся только к синтетическому тесту.

Причина, которую удалось подтвердить локально: раньше одна и та же комбинация параллели и состава memberships повторно проектировалась отдельно для каждого ученика. Сохранение персональной проверки для исключений и подтверждённых конфликтов обязательно, поэтому кэш ограничен идентичными входами. Причину конкретных 57 секунд production и число production-обращений к БД по этой неделе подтвердить не удалось: read-only запуск с production Supabase в рамках этой работы не состоялся. Production latency, число запросов и расклад времени не выдаются за измеренные.

### Изолированный полный маршрут

`scripts/schedule-regression/integration_flow.py` + `react-integration.mjs` прогнали настоящий React и SQLite-backed HTTP backend на disposable fixture с loopback egress:

- администратор в таблице недели связал четыре 5–6 направления в «Курс по выбору», затем четыре явно помеченных `digital` направления в «Цифровой трек»;
- preview проверил классы и слоты, сохранил реальные `teacher_overlap` и `room_overlap`, а кружок оставил вне Student Campus;
- одна изолированная неделя опубликована через интерфейс; Student Campus показал 5–6 по одной нейтральной карточке и 7–8 по одной карточке цифрового трека на слот;
- Teacher Campus сохранил четыре отдельных направления для соответствующих преподавателей.

Это синтетическое локальное окружение, не запуск production-недели `0637cbfc-2d83-492f-ae7e-3d4816830779`. Изображения администратора и preview публикации: [таблица и сопоставление](elective-blocks-admin-1366.png), [проверка перед публикацией](elective-blocks-publication-1366.png).
